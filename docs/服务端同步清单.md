# 服务端同步清单

本文专门说明：**哪些业务数据以服务端为准进行同步**，以及本地如何与之交互。  
不涉及房间内部棋盘实时同步细节（见 `服务端需求说明.md`），也不再使用「房间识别码」加入/展示。

> 加入房间：仅通过 **比赛列表 → 加入**。  
> 「开发者识别码」是管理员解锁口令，与已移除的房间识别码无关。

---

## 1. 总览

| 同步对象 | 服务端是否持有 | 本地能否独立使用 | 同步方向 |
| --- | --- | --- | --- |
| **选手列表** | 是（共享名册） | 是（本机缓存） | 本地 → 服务端，或 服务端 → 本地（用户选择） |
| **挂载列表** | 是 | 否（需连服查看） | 服务端 → 各客户端（列表拉取） |
| **历史赛程** | 是 | 否（需连服查看） | 服务端 → 各客户端（列表拉取） |

单机模式：不访问服务端；选手列表仅用本机；挂载/历史不可用。

持久化模型：房间、成员、历史、会话和公共名册保存到 Render Postgres；Node 进程只保留短期运行缓存。数据库不可用时 v2 写接口返回 503。

---

## 2. 选手列表（服务端共享名册）

### 2.1 是什么

选手列表 = 已保存的选手条目集合，供开赛/直播配置时快捷选用。  
每条至少包含：

| 字段 | 说明 |
| --- | --- |
| 名字 | 显示名（如「张三」） |
| 直播来源 | 平台 + 房间号/地址，或本地采集标记 |
| （可选）其它元数据 | 以实际实现字段为准 |

本机原先使用 `localStorage` 键 `bingotools_streamers`；连服后应与服务端名册对齐。

### 2.2 同步方式（用户主动选择）

本地提供两种操作（互不自动覆盖，除非用户点选）：

| 操作 | 方向 | 行为 |
| --- | --- | --- |
| **从服务端同步** | 服务端 → 本地 | 拉取服务端名册，合并进本机列表 |
| **同步到服务端** | 本地 → 服务端 | 把本机名册合并进服务端名册 |

### 2.3 去重规则（两种方向都必须做）

不论「从服务端同步」还是「同步到服务端」，合并后都要**自动删除重复内容**：

1. **判定重复的主键**（按优先级，实现须固定一种并写进接口说明）  
   - 首选：同一「直播来源」规范化后的值相同（平台 + 房间号/URL 规范化）视为同一人；  
   - 若无直播来源：同一「名字」（去空白、大小写规则固定）视为重复。  
2. **合并冲突**  
   - 同主键两条：保留较新的一条（以服务端/本机时间戳或最后修改时间为准）；名字不一致时以「目标侧用户刚确认的一侧」或「较新」为准，并在 UI 提示。  
3. **结果**  
   - 列表中不得出现重复主键；  
   - 同步完成后刷新下拉预设与直播配置列表。

### 2.4 权限与范围

| 角色 | 从服务端同步到本地 | 同步到服务端 |
| --- | --- | --- |
| 已连接的普通用户 | 允许（只读拉取合并） | 不允许；上传公共名册需要管理员权限 |
| 管理员 | 允许 | 允许（可覆盖/整理服务端名册） |
| 单机模式 | 不可连服；仅本机列表 | 不可 |

### 2.5 与房间的关系

- 选手列表是**全局共享名册**，不是某一场房间的成员列表。  
- 开赛时从名册选红/蓝选手，选中后可触发本地采集对应直播；选中结果写入本场 `match.left/right`，之后随房间同步，与名册本身独立。

### 2.6 实现状态说明

| 能力 | 状态 |
| --- | --- |
| 本机保存 / 导入导出选手 | 已有（本地） |
| 服务端名册存储与双向同步 API | 已实现：`/roster` 读取；`/roster/push` 由开发者上传合并 |

## 3. 挂载列表

### 3.1 是什么

挂载列表 = 服务端当前所有状态为 **`mounted`（已挂载 / 暂停）** 的房间摘要。

典型字段（列表展示）：

- 红方 vs 蓝方名称  
- 当前比分  
- 裁判名字  
- 已进行用时（挂载时冻结）  
- 成员人数  

### 3.2 如何同步到客户端

- 房间权威状态保存在服务端数据库，客户端只保存会话 token 和最近房间 ID。  
- 客户端通过 `POST /api/v2/list`（或比赛列表弹窗刷新）拉取；按状态分组展示「已挂载」。  
- **没有**「本地挂载列表再上传」；本机不能伪造挂载记录。  
- 轮询/手动「刷新 / 重连」会更新列表。

### 3.3 谁能改挂载列表（通过房间操作，而非直接改列表）

| 操作 | 结果 |
| --- | --- |
| 裁判「挂载并暂停」/「暂停比赛」 | 房间进入挂载列表 |
| 他人「接管」 | 离开挂载，回到等待或进行中 |
| 删除挂载（房主或管理员） | 从挂载列表消失 |
| 服务器重启 | 整表可能清空 |

### 3.4 加入方式

挂载中房间**不能**普通加入；只能「接管」（填写新裁判信息）。  
不再使用房间识别码进入。

---

## 4. 历史赛程

### 4.1 是什么

历史赛程 = 服务端当前所有状态为 **`ended`（比赛已结束）** 的房间摘要（赛程记录）。

典型字段：

- 对阵双方与最终比分  
- 裁判  
- 比赛用时  
- 结束相关播报状态（若有）  

### 4.2 如何同步到客户端

- 与挂载列表相同：经 `/list` 拉取，展示在「比赛已结束」分组。  
- 只读浏览为主；本地不单独存一份「权威历史库」。  
- 服务器重启后历史从数据库恢复；删除和重新挂载仍按服务端操作记录执行。

### 4.3 历史相关操作

| 操作 | 权限 | 效果 |
| --- | --- | --- |
| 查看详情 | 已连接用户 | 展示对阵、比分、用时、成员与记录等（**不含房间识别码**） |
| 重新挂载 | 原裁判或管理员 | 生成新的挂载房，并删除该条历史记录 |
| 删除记录 | 房主或管理员 | 从历史赛程移除 |

### 4.4 与「进行中 / 等待」的区分

| 列表分区 | 状态 | 是否算挂载 | 是否算历史 |
| --- | --- | --- | --- |
| 等待开始 | `waiting` | 否 | 否 |
| 比赛进行中 | `playing` | 否 | 否 |
| 已挂载（暂停） | `mounted` | **是** | 否 |
| 比赛已结束 | `ended` | 否 | **是** |

## 5. 客户端界面落点

| 同步对象 | 用户从哪里看 / 操作 |
| --- | --- |
| 选手列表 | 直播配置 / 开始比赛选手预设；「从服务端同步」「同步到服务端」按钮（按第 2 节） |
| 挂载列表 | 比赛列表 → 「已挂载（暂停）」分组 |
| 历史赛程 | 比赛列表 → 「比赛已结束」分组 |

比赛列表入口：工具栏「比赛列表」。单机模式下入口不可用。

## 6. 明确不在本清单内的内容

| 内容 | 说明 |
| --- | --- |
| 房间识别码 | **已移除**；不展示、不复制、不出现在 QQ 播报 |
| 开发者识别码 | 管理员口令，不是房间码 |
| 棋盘格点实时同步 | 属于「当前房间」会话内同步，见总需求文档 |
| QQ 群消息正文 | 服务端模板生成，用户不可自定义整段文案 |
| 本机美化 / 字体 / 单机计时 | 纯本地，不同步服务端 |

---

## 7. 验收要点（同步相关）

- [ ] 选手：从服务端同步后本机无重复项；同步到服务端后服务端无重复项  
- [ ] 选手：两种方向均可由用户主动触发，不会在后台静默互相覆盖  
- [ ] 挂载：A 机挂载后，B 机刷新列表可见；接管/删除后列表更新  
- [ ] 历史：结束后出现在历史分区；删除/重挂后记录按规则消失或转移  
- [ ] 界面与 QQ 播报均不再出现「房间识别码」  
- [ ] 加入仅通过列表「加入」按钮完成
