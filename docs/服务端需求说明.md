# BingoTools 服务端需求说明（完整版）

> 文档版本：与代码 `qqbot-service` **17.2.0** 对齐  
> 范围：云端 / 本机 Node 服务中**所有由服务端决定、配置、校验、持有或推送**的内容  
> 代码目录：`qqbot-service/`（主入口 `server.mjs`，房间 `rooms.mjs`，旧版比赛 `matches.mjs`，QQ 事件 `events.mjs`）  
> 默认云端地址：`https://bingotools-qqbot-api.onrender.com`

本文是**产品/联调需求文档**，描述「服务端负责什么、如何配置、谁能改、改完有什么效果」。  
客户端本地 UI（棋盘美化、字体、单机计时等）仅在与服务端发生边界时提及。

---

## 1. 目标与边界

### 1.1 服务端要解决的问题

1. **公开房间同步**：多台电脑共用同一房间列表、棋盘、比分、挂载/结束状态，无需每人持有密钥。  
2. **QQ 群播报**：比赛开始/结束、定时汇总、群内 @ 查询，统一发到管理员配置的**固定群**。  
3. **权限分层**：普通观众 / 本场裁判（房主）/ 管理员（开发者识别码解锁）。  
4. **防滥用**：频率限制、成员上限、房间容量、通知队列、全局 QQ 发送配额。

### 1.2 服务端明确不做的事

| 不做 | 说明 |
| --- | --- |
| 托管前端 HTML | 模式为 `api-only`；页面在本地或桌面 exe 内 |
| 直播拉流 / 同源代理 | 仍由 Wails / 本地播放逻辑负责 |
| 让用户自选 QQ 群 | 仅服务端环境变量中的固定 `QQ_GROUP_OPENID` |
| 让用户自定义群消息正文 | 仅固定模板字段 |
| 跨重启永久保存房间 | 由 Render Postgres 保存房间、会话和管理员授权时间；数据库不可用时 v2 明确返回 503 |
| 在单机模式下提供能力 | 单机模式完全不访问服务端 |

### 1.3 两套 API 并存（需求上必须分清）

| 体系 | 前缀 | 鉴权 | 用途 |
| --- | --- | --- | --- |
| **房间 v2（现行主路径）** | `/api/v2/*` | 匿名 `POST /session` 换 token，再 Bearer | 公开房间、挂载、管理员、定时汇总 |
| **比赛 v1（旧版 / QQ 播报兼容）** | `/api/v1/*` | 必须 `BOT_CLIENT_KEY` Bearer | 旧「开始/比分/结束」与测试播报；可挂可选数据库 |

桌面桥接白名单见 `internal/app/qqbot.go`：`CallRoomService` 仅放行固定 v2 路径 + `/health`；`CallQQBot` 仅三个 v1 比赛路径。

## 2. 部署与配置项（服务端设定的「静态配置」）

### 2.1 配置来源优先级

1. **进程环境变量**（Render Dashboard / 系统环境）——正式环境以此为准。  
2. **本地文件** `qqbot-service/.local-config.json`（仅本机；`RENDER` 环境变量存在时**忽略**）。  
3. 代码内默认值（端口、QQ API 地址等）。

本地写入配置：`npm run setup`（`setup-local.py`），文件权限建议 `0600`。  
**禁止**把含密钥的本地配置提交到 Git 或上传到 Render。

### 2.2 环境变量一览（必须写进部署清单）

| 变量名 | 是否必需 | 默认 / 示例 | 需求含义 |
| --- | --- | --- | --- |
| `PORT` | 否 | `8787`（Render 会注入） | HTTP 监听端口 |
| `HOST` | 否 | `0.0.0.0`；本地 setup 可写 `127.0.0.1` | 绑定地址 |
| `QQ_APP_ID` | 播报/事件必需 | — | QQ 机器人 AppID |
| `QQ_APP_SECRET` | 播报/事件必需 | — | QQ 机器人密钥；**永不下发客户端** |
| `QQ_GROUP_OPENID` | 播报必需 | — | **唯一**目标群；所有人共用 |
| `BOT_CLIENT_KEY` | v1 必需 | Blueprint 可自动生成 | 旧版/测试接口的使用密钥；未配置时 v1 返回 503 |
| `BINGOTOOLS_DEV_CODE` | 管理员功能必需 | — | 管理员「开发者识别码」；空则无法 `/dev-auth` |
| `QQ_EVENTS_ENABLED` | 否 | 非 `true` 则不连网关 | 为 `true` 时启用群 @ 查询 WebSocket |
| `QQ_API_BASE` | 否 | `https://api.sgroup.qq.com` | QQ OpenAPI 根地址 |
| `QQ_TOKEN_URL` | 否 | `https://bots.qq.com/app/getAppAccessToken` | 取 access_token |
| `ALLOWED_ORIGINS` | 否 | 文档兼容 | **当前实现不再按白名单拦截**；公开接口回显任意 `Origin` |
| `DATABASE_URL` / `SUPABASE_DATABASE_URL` | Render 必填；本地兼容 | 空 | Render 的 v2 房间和 v1 比赛使用 `DATABASE_URL`；本地未配置时仅允许内存测试模式 |
| `SUPABASE_CA_CERT` | 否 | — | 可选 TLS CA（`\n` 转义为换行） |
| `RENDER` | Render 自动 | — | 存在时跳过本地配置文件；限流 IP 取 `X-Forwarded-For` 最右侧 |
| `NODE_VERSION` | Blueprint | `24` | Render 构建用 |

### 2.3 Render Blueprint 要求

- 类型：Node Web Service（免费档可跑，有冷启动）。  
- 构建：`npm --prefix qqbot-service ci`  
- 启动：`npm --prefix qqbot-service start`  
- 健康检查路径：`/health`  
- 建议用 UptimeRobot 等探活 `/health`（无密钥、不触发 QQ 发送）。  
- 更新 CORS / 删除逻辑 / 房间权限后：**必须重新部署**，否则线上仍跑旧进程。

### 2.4 本地联调代理（非服务端进程，但是对接要求）

- 推荐：`node scripts/serve-html.mjs` → `http://127.0.0.1:8000/bingotools.html`  
- 同源路径 `/qqbot` 反代到云端（默认 `QQBOT_UPSTREAM=https://bingotools-qqbot-api.onrender.com`）。  
- 客户端在 localhost 下优先走 `/qqbot`，避免浏览器 CORS / 扩展拦截。

## 3. 运行时状态（服务端持有的「动态设定」）

运行缓存只在进程内存中；房间、会话、成员、播报状态、公共名册和管理设置落在 Render Postgres，服务重启后恢复。

### 3.1 实例身份

| 字段 | 说明 |
| --- | --- |
| `instance` | 启动时生成的 UUID；出现在 `/health` 与每个 v2 成功/部分错误响应中 |
| 客户端行为 | 若本地缓存的 `instance` 变化，仅提示服务器已重启并保留 token/房间，随后从数据库恢复 |

### 3.2 会话（Session）

| 项 | 要求 |
| --- | --- |
| 创建 | `POST /api/v2/session`，无需密钥 |
| Token | 32 字节随机 hex；响应 `{ token }` |
| 容量 | 最多 **10000** 会话，超出 → `503`「会话容量已满」 |
| 有效期 | 滑动 **30 天**；超时 → `401`「会话失效或服务器已重启，请重新连接」 |
| 会话内字段 | `id`（UUID）、`devUntil`（管理员解锁截止时间）、`creates`（创建幂等表，最多 100 条） |
| 限流 | 每 IP 每分钟最多 **30** 次 `/session` |

### 3.3 管理员解锁（开发者模式）

| 项 | 要求 |
| --- | --- |
| 配置 | 服务端 `BINGOTOOLS_DEV_CODE`（不可空上线若需要管理员能力） |
| 接口 | `POST /api/v2/dev-auth`，body `{ code }` |
| 成功 | `devUntil = now + 8 小时`，返回 `{ expiresAt }` |
| 失败 | 未配置 → `503`「服务端未设置开发者识别码」；错误 → `403`「识别码错误」 |
| 限流 | 每 IP 每分钟最多 **5** 次 |
| 退出 | `POST /api/v2/dev/logout` 立即清除解锁 |
| 权限效果 | 见第 5、6 节：多开房间、删他人挂载/已结束、改服务端定时汇总、可见服务器地址设置等 |

### 3.4 服务端定时群汇总（管理员可改）

| 项 | 要求 |
| --- | --- |
| 存储 | 数据库单例 `bingotools_settings`，默认 `{ enabled: false, interval: 5 }`（分钟） |
| 读写 | 管理员 `POST /api/v2/dev/settings`：空 body 读取；带 `{ enabled, interval }` 写入 |
| 校验 | `enabled` 必须布尔；`interval` 整数且 **5–1440**，否则「播报间隔须为 5–1440 分钟」 |
| 非管理员 | `403`「需要开发者权限」 |
| 触发 | 服务内 tick（约 250ms）；仅当 `enabled` 且存在「进行中」内容时发送 |
| 内容 | 进行中房间摘要（模板见第 7 节）；**挂载中房间不计入进行中** |
| 失败 | 错误写入 `settings.lastError`（经脱敏）；不自动无限重试 |

### 3.5 房间仓库

| 项 | 要求 |
| --- | --- |
| 容量 | 最多 **2000** 间；满时优先删除最旧的 `ended`；若无已结束可删 → `503`「房间容量已满，请稍后重试」 |
| 成员 | 每房最多 **10** 人（含裁判） |
| 在线判定 | 成员 `seen` 距今 **&lt; 30 秒** 视为在线 |
| 幂等创建 | `request_id` + 内容指纹；同 id 内容变 → `409`「同一次创建请求内容发生变化」 |
| 幂等重挂 | `remountByRequest` 最多记 **500** 条 |

### 3.6 全局限流与队列（所有用户合计）

| 机制 | 限额 | 超限文案 |
| --- | --- | --- |
| 会话请求 | 每会话 **240 次/分钟** | 「请求过于频繁，请稍后重试」 |
| 创建/重挂 | 每 IP **5 次/分钟** | 同上 |
| QQ 发送窗口 | 全实例 **12 次/分钟** | 「群播报过于频繁，请一分钟后重试（所有使用者合计每分钟最多 12 次）」 |
| 通知队列 | 间距约 **5.1s**，积压 ≤ **100** | 「群通知队列已满，请稍后重试」`429` |

### 3.7 棋盘 / 比分服务端校验规则（写入房间时）

服务端**不信任**客户端随意 JSON，创建/更新/结束时强制校验：

| 项 | 规则 |
| --- | --- |
| 棋盘对象 | 必须为对象；序列化长度 ≤ **120000** |
| 阵列字段 | `red/blue/first/marks/redTime/blueTime` 长度必须为 **25** |
| 标记 | 每格 ≤ **30** 条字符串，每条 ≤ **200** 字 |
| 格文本 | `cellTexts` 每格 ≤ **2000** |
| 结算历史 | 最多保留最近 **100** 条 |
| 计分设置 | 相关整数 **0–1000**；`rowScores` 长度 5 |
| 比分 | `red/blue` 有限数字，绝对值 ≤ **1e6** |
| 文本字段 | 去空白、禁控制字符；一般名称类 ≤ **100**；比赛侧 cleanText ≤ **512** |

不通过则拒绝写入并返回中文错误（如「棋盘数据无效」「比分无效」等）。

## 4. HTTP 与跨域（服务端对外契约）

### 4.1 公共端点（无需 BOT_CLIENT_KEY）

| 方法 | 路径 | 响应要点 |
| --- | --- | --- |
| `GET` | `/` | `{ ok, service, version: "17.2.0", mode: "api-only", health: "/health" }` |
| `GET` | `/health` | `{ ok, service, version, instance, qq }`，`qq` 为事件状态如 `ready` / `disabled` |
| `OPTIONS` | 任意 | `204` + CORS 头 |
| `POST` | `/api/v2/*` | 房间 API（见第 5 节） |

### 4.2 CORS 需求（现行）

- 回显请求的 `Origin`；无 Origin 时用 `*`。  
- 允许头：`Authorization, Content-Type, Idempotency-Key`。  
- 允许方法：`GET, POST, OPTIONS`。  
- **需求意图**：兼容本机各端口、Wails、Cursor 内置浏览器、`file://`（Origin 为字符串 `null`）。  
- 环境变量 `ALLOWED_ORIGINS` 可保留作运维文档，但**不得再作为拒绝条件**（旧版白名单会导致桌面/预览全面连不上）。

### 4.3 通用响应约定

- 成功 JSON 常含：`ok: true`，v2 另含 `instance`、`serverTime`。  
- 失败：`{ ok: false, error: "..." }`；错误串脱敏（去掉 AppSecret、BOT key、识别码等），最长约 **500** 字。  
- v2 请求体上限约 **128 KiB**；默认 JSON 体（v1）约 **16 KiB**，过大 →「request body is too large」。  
- v2 **仅接受 POST**，否则 `405`「请使用 POST」。

### 4.4 冷启动

- Render 免费实例休眠后，首个请求可能需数十秒唤醒。  
- 客户端允许等待约 **90 秒**；桌面桥接约 **85 秒**。  
- 超时提示需求：「唤醒服务超过 90 秒，请稍后重试」一类文案；**不因超时自动重复 QQ 播报**。

## 5. 房间 API v2（服务端业务核心）

除 `/session` 外，均需：`Authorization: Bearer <sessionToken>`。

### 5.1 接口清单与语义

| 路径 | 权限 | 请求要点 | 成功结果 / 关键规则 |
| --- | --- | --- | --- |
| `/session` | 无 | `{}` | 发放 token |
| `/dev-auth` | 会话 | `{ code }` | 管理员 8 小时 |
| `/dev/logout` | 会话 | `{}` | 清除管理员 |
| `/dev/settings` | **管理员** | 读：`{}`；写：`{ enabled, interval }` | 定时汇总设定 |
| `/list` | 会话 | `{}` | `{ rooms, developer }`；列表**不含 board** |
| `/roster` | 会话 | `{}` | 读取服务端共享选手名册；普通用户可用 |
| `/roster/push` | 管理员 | `{ entries }` | 将本地名册合并到服务端；同直播来源自动去重 |
| `/create` | 会话 | `match, board, scores, request_id?` | 新房 `waiting`；非管理员同时只能有一个未结束未挂载房 |
| `/get` | 会话 | `{ id }` | 完整房间（含 board） |
| `/join` | 会话 | `{ id, name? }` | `mounted/ended` 不可加入；满员 10 人拒绝 |
| `/heartbeat` | 成员 | `{ id }` | 刷新在线；非成员 → 403「你已离开或被移出房间」 |
| `/leave` | 成员 | `{ id }` | 进行中裁判不可离开：「裁判请先结束或挂载比赛」 |
| `/update` | 裁判/管理员 | `{ id, revision, board, scores }` | 仅 `waiting`/`playing` |
| `/settings` | 裁判/管理员 | `{ id, revision, countdown }` | `countdown` 整数 **0–60**（秒）；当前无完整倒计时状态机落库到 `countdown` 状态 |
| `/kick` | 裁判/管理员 | `{ id, revision, member }` | 不能踢裁判本人 |
| `/start` | 裁判/管理员 | `{ id, revision }` | → `playing`，触发开始播报；已是 playing 则幂等返回 |
| `/mount` | 裁判/管理员 | `{ id, revision }` | → `mounted`，冻结用时；记录 mount |
| `/end` | 裁判/管理员 | `{ id, revision, board, scores }` | → `ended`，触发结束播报；已是 ended 幂等 |
| `/takeover` | 任意会话（挂载房） | `{ id, revision, referee }` | 仅 `mounted`；接管后成为新裁判 |
| `/remount` | 原房裁判/管理员 | `{ id, request_id }` | 仅 `ended`；生成新 `mounted` 房并**删除**旧 ended |
| `/retry` | 裁判/管理员 | `{ id, kind: start\|end }` | **仅** delivery 为 `failed` 可重试；`unknown` 禁止自动重试 |
| `/delete` | 见下 | `{ id }`（**不校验 revision**） | 见 5.3 |

未知路径：`404`「接口不存在」。房间不存在：`404`「房间已被删除，或数据库中没有该记录」。

### 5.2 房间状态机（需求）

```text
create ──► waiting
              ├─ start ──► playing ──┬─ mount ──► mounted ── takeover ──► waiting|playing
              │                      └─ end ────► ended ── remount ──► (新 id) mounted
              ├─ mount ──► mounted
              └─ end ────► ended

delete：房主可删自己的任意状态房间；
        管理员可删「他人」的 mounted / ended。
```

说明：

- UI 文案中有「准备倒计时」状态名，但服务端**当前没有**把 `state` 设为 `countdown` 的完整路径；`/settings` 仅保存倒计时秒数字段。  
- `mounted`：**暂停同步意义上的挂载**（用时冻结、不可普通加入，需接管）。  
- `ended`：进入历史区；可重挂或删除。

### 5.3 删除权限（明确需求，与旧文档差异）

| 角色 | 可删除对象 |
| --- | --- |
| **房主（本场裁判）** | 自己房间的**任意状态**（含 waiting/playing） |
| **管理员** | 任意用户的 **`mounted` 或 `ended`**；不可删别人正在进行的 waiting/playing |
| **观众** | 不可删除 |

实现要求：

- **不依赖**列表里的 `revision`（避免「点了删除却 409」）。  
- 客户端可对旧云端做兼容：若仍 409，则先 `/get` 再带 revision 重试。  
- 线上必须部署含本逻辑的 `rooms.mjs`，否则仍会出现「管理员删不了已结束」。

### 5.4 并发与修订号

- 修改类接口（update/start/mount/end/kick/settings/takeover 等）使用 `revision` CAS。  
- 不匹配 → `409`「房间已更新，请刷新后重试」。  
- 客户端应拉最新房间后再操作；删除接口按 5.3 豁免 revision。

### 5.5 角色字段（下发给客户端）

每个房间视图需包含：

| 字段 | 含义 |
| --- | --- |
| `isHost` | 当前会话是否本场裁判 |
| `canControl` | 裁判 **或** 管理员 |
| `developer`（仅 list） | 当前会话是否管理员 |
| `members[].online` / `isSelf` | 在线与是否本人 |
| `elapsed_seconds` | 服务端计算的用时 |
| `delivery.start/end` | 播报状态：`pending` / `sent` / `failed` / `unknown` |

## 6. 权限矩阵（汇总）

| 能力 | 观众 | 房主 | 管理员 |
| --- | --- | --- | --- |
| 连接 / 列房间 / 查看 / 加入 / 心跳 / 离开 | ✓ | ✓ | ✓ |
| 创建房间 | ✓（同时仅 1 个进行中） | — | ✓（可多开） |
| 改棋盘 / 踢人 / 开始 / 挂载 / 结束 / 重试播报 | ✗ | ✓ | ✓（对有权房间） |
| 接管挂载房 | ✓（满足状态与 revision） | — | ✓ |
| 重挂已结束 | ✗ | ✓ | ✓ |
| 删除房间 | ✗ | 自己任意状态 | 他人挂载/已结束 |
| 改服务器地址 UI | ✗ | ✗ | ✓（客户端展示） |
| 改定时群汇总 | ✗ | ✗ | ✓ |
| 使用 v1 + BOT_CLIENT_KEY | 持有密钥者（运维向） | 同左 | 同左 |

非房主且非管理员操作控制接口 → `403`「只有本场裁判可以操作」。

## 7. QQ 播报与查询（服务端内容规范）

### 7.1 谁能触发发送

| 来源 | 触发条件 |
| --- | --- |
| 房间 v2 `/start` | 进入 playing |
| 房间 v2 `/end` | 进入 ended |
| 房间 v2 `/retry` | 对应 delivery 为 `failed` |
| 定时汇总 | 管理员开启且存在进行中房间 |
| v1 `/matches/start|end`、`/qq/test` | 持有 `BOT_CLIENT_KEY` |
| 群 @ 机器人 | `QQ_EVENTS_ENABLED=true` 且事件群 = 配置群 |

所有发送进入同一通知队列 + 全局 12 次/分钟配额。

### 7.2 消息模板（字段级需求）

**开始（含测试）**

- 标题：`🎮 Bingo 比赛开始`（测试为带「（测试）」）  
- 北京时间、裁判直播间地址、裁判名  
- 红方 / 蓝方名称与直播间  
- **不附带房间识别码**（产品已移除）

**进行中汇总 / 结束**

- 进行中：`🎮 正在进行的 Bingo 比赛`  
- 结束：`🏁 Bingo 比赛结束`  
- 裁判、直播间、红蓝比分、用时、同步时间（**不含**房间识别码）  


**直播间地址规范化**

| 输入 | 服务端行为 |
| --- | --- |
| `local` | 文案「本地采集（无直播间地址）」 |
| B 站数字房号 | 规范化为直播 URL |
| 抖音 slug/数字 | 规范化为直播 URL |
| 完整 http(s) | 校验后使用 |
| URL 含账号密码 | 拒绝：「直播间地址不能包含账号密码」 |

### 7.3 投递状态机（每房间 start/end）

```text
发送前 → pending → 成功 sent
                 → 明确失败 failed（允许 /retry）
                 → 不确定 unknown（HTTP≥500 或无 message id；禁止自动重试，提示核对 QQ 群）
```

**比分同步不得刷屏发群**；仅开始、结束、定时汇总、@ 查询会发消息。

### 7.4 @ 查询

- 仅处理目标群的 `GROUP_AT_MESSAGE_CREATE`。  
- 回复内容：当前 v2 进行中 + v1 遗留进行中摘要，总长截断约 **3500** 字，超出提示「其余比赛暂未展示。」  
- 需带 `msg_id` / `msg_seq` 等回复字段（实现细节见 `events.mjs`）。

## 8. 旧版比赛 API v1（仍属服务端设定）

### 8.1 鉴权

- 所有 `/api/v1/*`：`Authorization: Bearer <BOT_CLIENT_KEY>`（timing-safe 比较）。  
- 未配置 key → `503`「服务端尚未配置 BOT_CLIENT_KEY」。  
- key 错误 → `401`「invalid client key」。

### 8.2 端点需求

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/v1/qq/status` | 事件状态、是否配置目标群、发现的群列表摘要 |
| GET | `/api/v1/qq/groups` | 内存中发现过的群 |
| POST | `/api/v1/qq/test` | 校验 payload 并发送**测试**开始文案（不建房间） |
| POST | `/api/v1/matches/start` | 需 `Idempotency-Key`（8–128，`[A-Za-z0-9_-]`）；开赛播报 |
| POST | `/api/v1/matches/score` | `{ match_id, revision≥1, scores, elapsed_seconds? }`；**不发群** |
| POST | `/api/v1/matches/end` | 锁定终局并结束播报 |

### 8.3 持久化策略（v1）

| 条件 | 行为 |
| --- | --- |
| 未配置数据库 URL | 本地开发可使用内存测试模式；Render 生产环境拒绝提供 v2 房间接口并返回数据库未就绪 |
| 配置了 URL 但库未就绪 | **拒绝写入**（不向 QQ 假装成功）：「比赛记录数据库未就绪；尚未向 QQ 发送」 |
| 库就绪 | 使用 `bingotools_live_matches`（见 `schema.sql`） |

房间 v2 **不依赖**该库。

### 8.4 裁判 / 选手 payload 校验（服务端）

- 必须有裁判 `room` + `title`。  
- `started_at` 合法日期（可默认现在）。  
- 平台与直播地址规则同第 7.2 节。  
- 选手展示名来自客户端棋盘侧逻辑时，服务端仍校验结构与地址。

## 9. 客户端与服务端的职责分界（避免需求混淆）

### 9.1 仅存客户端（服务端无对应设定）

- 单机模式开关 `offlineMode`  
- 备注区骰子/连接面板显隐、美化、字体、侧栏布局  
- 本地用户名（加入房间时带上，服务端只存成员名）  
- 本地裁判信息草稿、直播采集源  
- QQ Bot 服务地址缓存（管理员可改；默认云端 URL）  
- 单机下「开始计时 / 暂停 / 重置」（**不创建房间、不发 QQ**）

### 9.2 必须由服务端裁定

- 房间是否存在、状态、revision、成员列表  
- 谁是裁判 / 是否管理员  
- 能否创建第二间房  
- 播报是否已发送及失败原因  
- 定时汇总开关与间隔  
- 全局限流与队列是否接受新发送  
- 棋盘写入合法性  

### 9.3 单机模式边界（产品需求）

开启后：

- **禁止**访问 session/list/create/join/mount/delete/dev-auth 等一切房间云能力。  
- 比赛计时按钮变为本地秒表，**不弹**开始比赛表单。  
- 连接面板显示「单机模式」。  
- 关闭单机后才重新连接与管理员验证。

## 10. 安全与运维需求

1. **密钥永不进前端包**：`QQ_APP_SECRET`、`BOT_CLIENT_KEY`、`BINGOTOOLS_DEV_CODE` 仅服务端。  
2. 错误回显必须脱敏。  
3. 桌面 `CallRoomService` / `CallQQBot`：禁止任意 URL 代理；HTTPS（本机 http 调试除外）；禁止跟随会带走 Bearer 的重定向。  
4. 管理员识别码与 QQ AppSecret **不得混用**。  
5. 免费实例：接受冷启动；用 `/health` 探活；重要场次前先唤醒。  
6. 变更房间删除、CORS、权限后必须 **Render 重新部署**，并通知客户端强刷或重装。  
7. 数据库模型：历史房间和已结束列表跨重启保留；数据库不可用时必须显示保存失败。
